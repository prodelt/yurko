# Research: почему прод не достаёт до rada.gov.ua

**Дата:** 2026-09-03
**Роль:** `infra-egress`
**Статус:** диагноз установлен, воспроизведён и починен в лабораторных условиях. Кода проекта не менялось.

---

## TL;DR

`rada.gov.ua` **отбрасывает TLS-соединение, если ClientHello больше ~700–900 байт**. База
прод-образа `python:3.12-slim` бесшумно переехала с Debian 12 (OpenSSL 3.0) на **Debian 13
«trixie» с OpenSSL 3.5.7**, который по умолчанию добавляет постквантовый key share
`X25519MLKEM768` и раздувает ClientHello с ~324 до **1554 байт**. Такой ClientHello Рада
рвёт в 76–100 % случаев — ровно с тем `UNEXPECTED_EOF_WHILE_READING`, что видно на проде.

**Это не WAF, не бан IP датацентра, не DNS, не таймаут и не SECLEVEL.** Ни одна из этих
гипотез не выдержала проверки (раздел «Отвергнутые гипотезы»).

**Рекомендация:** зафиксировать список TLS-групп через `OPENSSL_CONF` в `Dockerfile`
(2 строки, 0 строк Python-кода, 0 ₴). Проверено живьём: 15/15 успешных хендшейков к Раде
и 6/6 к каждому из шести остальных внешних хостов проекта.

---

## 1. Что именно рвётся

Рвётся **TLS-хендшейк**, на самом первом шаге. Соединение TCP устанавливается, клиент
отправляет ClientHello, после чего сервер закрывает соединение, не отправив ServerHello.
HTTP-обмена не происходит вообще — поэтому нет ни 403, ни любого другого HTTP-статуса.

Оба «разных» хоста Рады — **это один и тот же сервер**:

```
$ nslookup data.rada.gov.ua
Name:    zakon.rada.gov.ua
Address: 193.19.153.66
Aliases: data.rada.gov.ua
```

`data.rada.gov.ua` — CNAME на `zakon.rada.gov.ua`, один IP `193.19.153.66`. То есть оба
симптома из тикета (`query_law` и `discover_laws`) — **один дефект, а не два**.

Для сравнения: `reyestr.court.gov.ua` → `212.90.190.162`, другой сервер, другой фронт —
поэтому `search_court_decisions` и работает.

---

## 2. Корневая причина

### 2.1. База прод-образа переехала на Debian 13

`Dockerfile:1` — `FROM python:3.12-slim`, **без пина на релиз Debian**. Тег `3.12-slim`
переехал на trixie при выходе Debian 13:

```
$ docker run --rm python:3.12-slim sh -c 'grep PRETTY /etc/os-release; python -c "import ssl,sys;print(sys.version.split()[0]);print(ssl.OPENSSL_VERSION)"'
PRETTY_NAME="Debian GNU/Linux 13 (trixie)"
3.12.14
OpenSSL 3.5.7 9 Jun 2026
```

Против dev-машины:

```
python 3.11.6 / OpenSSL 3.0.11 19 Sep 2023
```

`git log --follow -- Dockerfile` → единственный коммит `1f47073 feat: v1.2.0`. **Файл не
менялся; сломалась база под ним.** Это классическая регрессия «unpinned base image».

### 2.2. OpenSSL 3.5 раздувает ClientHello постквантовым key share

OpenSSL 3.5 по умолчанию предлагает гибридную группу `X25519MLKEM768`, чей публичный ключ
занимает 1216 байт. Замер размера ClientHello внутри прод-образа:

| конфигурация | размер записи ClientHello |
|---|---|
| дефолт OpenSSL 3.5.7 (с PQ) | **1559 B** (`length 0612` + 5) |
| с пином групп `X25519:P-256:P-384` | **324 B** (`length 0144` + 5) |

### 2.3. Сервер Рады не переваривает большой ClientHello

Замер «доза–эффект» **внутри прод-образа**, перемежая размеры друг с другом, чтобы
исключить плавающую доступность сервера (8 попыток на размер, padding через ALPN,
постквантовые группы отключены — то есть меняется **только размер**):

| размер ClientHello | ok | fail | доля отказов |
|---|---|---|---|
| 358 B | 8 | 0 | 0 % |
| 665 B | 8 | 0 | 0 % |
| 975 B | 4 | 4 | 50 % |
| 1285 B | 3 | 5 | 63 % |
| 1750 B | 0 | 8 | **100 %** |

Порог — между 665 и 975 байтами. Зависимость монотонная и воспроизводимая.

Важно: **padding сделан через ALPN, а не через постквантовые группы.** Значит, дело не в
`X25519MLKEM768` как таковом и не в незнакомом сервером алгоритме, а именно в **размере**
ClientHello. PQ-группа — лишь способ, которым OpenSSL 3.5 переваливает через порог.

Сервер при этом отвечает не молчаливым TCP-RST, а ломает запись протокола — OpenSSL
фиксирует `fatal decode_error` и затем EOF:

```
>>> TLS 1.3, Handshake [length 0636], ClientHello
>>> TLS 1.3, Alert [length 0002], fatal decode_error
error:0A000126:SSL routines::unexpected eof while reading
```

Типичный отпечаток старого TLS-терминатора/балансировщика, который читает ClientHello
одним чтением и не собирает его, если тот не поместился в первый буфер/сегмент.

### 2.4. Воспроизведение прод-ошибки один в один

В образе `python:3.12-slim`, дефолтный `ssl.create_default_context()`, 15 попыток:

```
python ssl default ctx -> ok 7 fail 8
last error: SSLEOFError: [SSL: UNEXPECTED_EOF_WHILE_READING] EOF occurred in violation of protocol (_ssl.c:1010)
```

Строка ошибки **побайтово совпадает** с той, что тикет снял с прода.

Контрольный замер на предыдущей базе:

```
$ docker run --rm python:3.12-slim-bookworm ...
OS-baseline: OpenSSL 3.0.20
bookworm default ctx -> ok 14 fail 1 (TimeoutError, не SSLEOFError)
```

Debian 12 / OpenSSL 3.0 — работает. Debian 13 / OpenSSL 3.5 — нет. **Разница только в базе
образа.**

## 3. Отвергнутые гипотезы

| гипотеза | вердикт | доказательство |
|---|---|---|
| **SECLEVEL=2 / отключены legacy-шифры** (ведущая гипотеза тикета) | **Опровергнута** | В `/etc/ssl/openssl.cnf` Debian 13 **нет ни одной** директивы `SECLEVEL`, `CipherString` или `MinProtocol`. Более того, Рада согласовывает вполне современный набор: `TLSv1.2 / ECDHE-RSA-AES256-GCM-SHA384 / rsa_pss_rsae_sha256 / P-256`. Никакого legacy-шифра в согласовании нет — понижать SECLEVEL нечему. |
| **Блокировка по IP датацентра (WAF Рады против облаков)** | **Опровергнута** | Отказ воспроизведён **с dev-машины**, то есть с того самого IP, с которого Python 3.11 успешно качает те же URL. Один IP, один момент времени: старый стек — 200, новый образ — `SSLEOFError`. IP тут ни при чём. Плюс пин групп чинит проблему, не меняя IP. |
| **WAF/антибот** | **Опровергнута** | WAF отдаёт HTTP-ответ (403/429/челлендж). Здесь HTTP-обмена нет вообще: разрыв до ServerHello. Ни одного HTTP-статуса ни в одной из ~150 попыток. |
| **DNS** | **Опровергнута** | Оба хоста резолвятся корректно и одинаково с dev и из контейнера в `193.19.153.66`; TCP-коннект устанавливается всегда. |
| **Таймаут / медленный источник** | **Опровергнута** | Отказы мгновенные (`SSLEOFError`, не `TimeoutError`), при `timeout=20..30`. Успешные ответы с тем же клиентом приходят за секунды: 216 531 B и 13 444 368 B. |
| **Отсутствие IPv4/IPv6** | **Не подтверждена, не требуется** | `193.19.153.66` — IPv4, соединение по нему устанавливается всегда. |
| **Специфично для «класса хостов со старым TLS»** | **Частично верно, но узко** | Из 7 внешних хостов проекта порог по размеру ClientHello ловит **только** `rada.gov.ua` (оба имени). `openrouter.ai`, `generativelanguage.googleapis.com`, Supabase pooler, `prozorro.gov.ua`, `api.telegram.org` — все TLS 1.3, дефолтный ClientHello, 6/6 ok. |

Отдельная заметка: `reyestr.court.gov.ua` недоступен **с этой dev-сети** (TCP-connect
timeout и с хоста, и из контейнера), но с прода работает. Это никак не связано с дефектом
Рады и на диагноз не влияет.

## 4. Проверенное исправление

### Вариант A (рекомендуемый): пин TLS-групп через `OPENSSL_CONF` — 0 строк Python

Действует на **весь процесс и все библиотеки сразу** (requests, urllib3, httpx, psycopg,
aiogram), не требует правки ни одного вызова и не может быть «забыт» в новом коде.

В `Dockerfile` (реализация — тикет 02):

```dockerfile
RUN cp /etc/ssl/openssl.cnf /etc/ssl/openssl-small-hello.cnf \
 && sed -i '/^\[openssl_init\]/a ssl_conf = ssl_sect' /etc/ssl/openssl-small-hello.cnf \
 && printf '\n[ssl_sect]\nsystem_default = system_default_sect\n\n[system_default_sect]\nGroups = X25519:P-256:P-384\n' \
      >> /etc/ssl/openssl-small-hello.cnf
ENV OPENSSL_CONF=/etc/ssl/openssl-small-hello.cnf
```

Существенная деталь: `ssl_conf` нужно вписывать **в уже существующую секцию
`[openssl_init]`** Debian-конфига (там же живёт `providers = provider_sect`). Первая
попытка добавить свою секцию `[default_conf]` в конец файла молча не сработала —
Debian-овское `openssl_conf = openssl_init` перебивает её, и отказы сохраняются. Это
единственная ловушка в данном фиксе.

Живая проверка в образе `python:3.12-slim`, 6 попыток на хост:

```
zakon.rada.gov.ua                     ok=6 fail=0  TLSv1.2
data.rada.gov.ua                      ok=6 fail=0  TLSv1.2
openrouter.ai                         ok=6 fail=0  TLSv1.3
generativelanguage.googleapis.com     ok=6 fail=0  TLSv1.3
aws-0-eu-west-1.pooler.supabase.com   ok=6 fail=0  TLSv1.3
prozorro.gov.ua                       ok=6 fail=0  TLSv1.3
api.telegram.org                      ok=6 fail=0  TLSv1.3
```

Плюс: доверие к CA не ломается (`verify_mode: CERT_REQUIRED`, 150 CA загружено), TLS 1.3 к
современным хостам сохраняется, `X25519` остаётся первым в списке.

Отдельно — 15/15 успешных хендшейков к Раде против 5–7/15 на дефолте.

**Проверка ровно того `Dockerfile`-сниппета, что рекомендуется выше** (образ собран
`docker build`, конфиг применился — `ssl_conf = ssl_sect` встал внутрь `[openssl_init]`),
живые запросы по реальным URL проекта:

```
OpenSSL: OpenSSL 3.5.7          # база не откатывалась, остался trixie
  zakon print   ok= 9 fail= 1 bytes=216531      (первый прогон, 10 попыток)
  data doc.zip  ok=10 fail= 0 bytes=13444368
  requests GET  ok:25/25                        (повторный прогон, 25 попыток)
  raw handshake ok:25/25
```

Суммарно по собранному образу: **81 успех из 82** запросов к Раде. Единственный отказ —
одиночный `SSLError` в первом прогоне, который не воспроизвёлся ни разу в последующих 50
попытках; это фоновая нестабильность самого сайта Рады, а не остаточный эффект дефекта
(дефект давал 76–100 % отказов, а не 1 %). При проектировании приёмки в тикете 02 стоит
закладывать 1–2 ретрая на фоновую флуктуацию источника.

### Вариант B (запасной): кастомный `ssl_context` в `HTTPAdapter`

```python
class SmallHelloAdapter(HTTPAdapter):
    def init_poolmanager(self, *a, **kw):
        ctx = ssl.create_default_context()
        ctx.set_ecdh_curve("prime256v1")
        kw["ssl_context"] = ctx
        return super().init_poolmanager(*a, **kw)
```

Живая проверка в прод-образе по реальным URL проекта, 8 попыток на URL:

```
=== BASELINE (stock requests) ===
  zakon print    ok=2 fail=6  bytes=216531
  data doc.zip   ok=4 fail=4  bytes=13444368

=== WITH FIX (small ClientHello) ===
  zakon print    ok=8 fail=0  bytes=216531
  data doc.zip   ok=8 fail=0  bytes=13444368
```

16/16 успехов, размеры совпадают с эталонными замерами с dev-машины (216 531 B).

**Минусы против варианта A:**
- `ssl.SSLContext.set_ecdh_curve()` в Python 3.12 **не принимает список** — проверено:
  `ValueError: unknown elliptic curve name 'X25519:prime256v1'`. Значит, приходится жёстко
  прибивать **одну** кривую `prime256v1` для всех хостов этой сессии. (`SSLContext.set_groups()`
  появился только в Python 3.13, в текущем образе его нет.)
- Чинит только тот HTTP-клиент, куда его смонтировали. `scraper.py` сейчас зовёт
  `requests.get(...)` напрямую (строки 147 и 207), без `Session`, — то есть тикету 02
  пришлось бы сначала завести общую сессию.

### Вариант C (дополнительно, к любому из вариантов): пин базы образа

`FROM python:3.12-slim-bookworm` вернул бы OpenSSL 3.0 и снял симптом сегодня, но это
консервация: bookworm уйдёт с поддержки, и проблема вернётся при следующем вынужденном
апгрейде. Как **самостоятельный** фикс не рекомендуется; как страховка вместе с A —
разумно пинить базу по digest, чтобы образ впредь не переезжал между релизами Debian молча.

## 6. Что передать в тикет 02

1. Основное: `OPENSSL_CONF` с `Groups = X25519:P-256:P-384`, вписать `ssl_conf` **внутрь
   существующей `[openssl_init]`** (иначе молча не применится).
2. Рядом: запинить базовый образ по digest, чтобы Debian больше не переезжал молча.
3. Приёмка — живая, не мок: `query_law("2341-14")` и `discover_laws("Кримінальний кодекс")`
   с прода; ожидать 216 531 B на `/laws/show/2341-14/print` и ~13.4 MB на `doc.zip`.
   Прогонять **минимум 8–10 раз подряд**: дефект вероятностный (76 %, не 100 %), поэтому
   один успешный запрос доказательством починки не является — именно так эта проблема и
   могла выглядеть «плавающей».
4. Регрессионный тест без сети: проверять, что итоговый `ssl.SSLContext` даёт ClientHello
   меньше ~600 B (или просто что список групп не содержит `MLKEM`). Живых сетевых вызовов в
   тестах не добавлять — constitution, пункт V.

## Приложение: как воспроизвести

```bash
# 1. Показать, что база переехала
docker run --rm python:3.12-slim sh -c 'grep PRETTY /etc/os-release; python -c "import ssl;print(ssl.OPENSSL_VERSION)"'

# 2. Воспроизвести прод-ошибку (ожидать ~50-75% отказов)
docker run --rm python:3.12-slim python -c '
import ssl,socket
ok=fail=0
for _ in range(15):
    try:
        s=socket.create_connection(("zakon.rada.gov.ua",443),timeout=20)
        ssl.create_default_context().wrap_socket(s,server_hostname="zakon.rada.gov.ua"); ok+=1
    except Exception as e: fail+=1; print(type(e).__name__, e)
print("ok",ok,"fail",fail)'

# 3. Показать, что дело в размере, а не в PQ-группах
docker run --rm python:3.12-slim sh -c '
A=$(for i in $(seq 1 40); do printf ",pad-%s" $i; done | cut -c2-)
echo | openssl s_client -connect zakon.rada.gov.ua:443 -servername zakon.rada.gov.ua -groups P-256 -alpn "$A" -msg -brief 2>&1 | grep -Ei "ClientHello|Alert|error"'
```

**Все замеры в этом отчёте сняты живьём 2026-09-03** внутри образа `python:3.12-slim`
(Debian 13 / OpenSSL 3.5.7) и на dev-машине (Windows / OpenSSL 3.0.11 и 3.5.3).
Код проекта не изменялся.
